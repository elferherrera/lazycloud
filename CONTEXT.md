# lazycloud — Context

## What it is

A terminal UI (TUI) application for browsing Google Cloud Platform (GCP) resources. It fetches resources via the GCP APIs on demand, caches them in a local SQLite database, and renders them in browsable tables. Think "lazygit/lazydocker for GCP".

## Tech stack

- Go 1.27 (module name: `lazycloud`)
- [tview v0.42.0](https://github.com/rivo/tview) — TUI widget toolkit
- [tcell v2 v2.8.1](https://github.com/gdamore/tcell) — terminal event layer
- `cloud.google.com/go/compute`, `cloud.google.com/go/resourcemanager`, `google.golang.org/api` — GCP SDK clients
- [mmaid-go v0.6.1](https://github.com/aaronsb/mmaid-go) — renders mermaid diagrams as terminal art (routes next-hop chart)
- `gopkg.in/yaml.v3` — yaml output of the `:write` command and the `config.yaml` config file
- `modernc.org/sqlite` — pure-Go SQLite driver (no cgo)

## Views

Each view is a `viewDef` struct (views.go) registered by view kind in `views` map (state.go). Fields: `title`, `headers`, `load` (read from cache), `refresh` (fetch from GCP API + save to cache), `fetch` (sync fetch+save+log core of the per-project views' `refresh`, wrapped into `refresh` by `projectRefresh` and run per view by `U`), `selectRow` (Enter on a row), `resource` (row cells → underlying cached resource, used by `y` copy JSON, `v` row details and detail filtering; `y` yanks a combined JSON object — the cached resource fields plus a `Columns` object mapping the view headers to the rendered row cells, so computed/derived columns like Route Exchange, Connections counts or Target Project are included — `rowCopyPayload` in handlers.go), `details` (optional: overrides the `v` details window body — when set, `showRowDetails` renders the resolved resource through it instead of the generic `appendRowDetails` JSON tree; the roles views use it to print each permission on its own line), `samples` (zero-value resource structs used to validate detail filter paths), `consoleURL` (open GCP Console in browser).

**Review when adding a new view** — a view is wired into several per-view registries beyond the `views` map, and each one silently degrades if missed:

- view-kind constants and the `xViewKind()` AllProjects helper (state.go), the `views` map entry, and — for per-project views — the `projectViewKinds` list so `U` refreshes it (views.go)
- a `:command` entry in `viewCommands` (handlers.go)
- a `view_updates` entry: every view (old and new) must record its refreshes in the cache's `view_updates` table, keyed `(view kind, project_id)` — one row per view per project, so refreshing the same view in two projects updates two separate rows (per-project views pass the fetched project; scoped views — workloads, node pools, DNS records, bucket IAM — pass their fetch project: the cluster/zone/bucket project; `…All` variants and the projects/public-images views pass the active `appState.ProjectID`). `Run` seeds one baseline row per registered kind at startup (`cache.SeedViewUpdates(viewKindNames())`, under empty project), and every successful refresh must call `a.markViewUpdated(kind, projectID)` (app.go) — `projectRefresh` covers per-project views automatically, `refreshProjectViews` (`U`) marks each fetched kind, and bespoke refresh closures call it themselves right before their completion `QueueUpdateDraw`
- `viewShortcutAction` (shortcut_config.go): the base kind's show function and, for `…All` kinds, the generic case — without it a numeric shortcut configured for the view is rejected as unknown
- the `a` all-projects toggle: `toggleAllProjects` (handlers.go) switches on the view's kind(s). A dual (per-project/all) view must have a case re-entering it via its `xViewKind()` helper; a scoped view with no all variant (projects, workloads, dns-records, nodepools, public-images) must join the explicit no-op case. A missing case leaves `AllProjects` flipped but the view unchanged — the per-project variant keeps rendering (no Project column) and `u` keeps fetching only the current project.

### Workload fetching

GKE workloads are Kubernetes resources, so `ListClusterWorkloads` shells out: it writes credentials to a temp `KUBECONFIG` via `gcloud container clusters get-credentials` (zone vs region flag inferred from the location's dash count) and runs `kubectl get deployments,statefulsets,daemonsets --all-namespaces -o json`, parsing items into `Workload` (Replicas as `ready/total`). The workloads view is cluster-scoped: pressing `w` on a clusters-view row sets `appState.Cluster`/`appState.ClusterProject` and switches to it; there is no numeric shortcut or `:command`. Workloads are cached per `(project, cluster)` in the `workloads` table (rows carry their cluster reference) and `refresh` re-fetches only the focused cluster. Requires `gcloud` and `kubectl` on PATH. In the workloads view `g` opens the GKE workload overview filtered by namespace, `l` opens Logs Explorer with a `k8s_container` query (project/location/cluster/namespace/pod-app from the focused row), `e` opens Logs Explorer with a `log_id("events")` + `resource.type="k8s_cluster"` query (cluster/location/project labels plus the workload name as a free-text match, via `GCPWorkloadEventsURL`), and `c` opens a shell with the kubectl context set (`openWorkloadShell` in view_workloads.go): the kubeconfig context name is resolved first via `kubectl config get-contexts -o name` (`kubectlClusterContext` → `findClusterContextName`: exact `gke_<project>_<location>_<cluster>` built from the cached cluster, else the first context ending in `_<cluster>` preferring ones containing the project, else the first containing the cluster name; no match aborts with a hint to fetch credentials first), then the TUI suspends, `kubectl config set-context <context> --namespace <namespace>` runs in the terminal (namespace from the focused row — in the user's default kubeconfig, not the fetcher's temp one), then an interactive `$SHELL` (fallback `/bin/sh`) takes over the terminal and stays open (`workloadShellCommand`: `LAZYCLOUD_CONTEXT=true` is added to its environment so nested commands can detect the lazycloud shell; the var exists only inside the shell — `checkNestedExecution` at the top of `Run` makes lazycloud refuse to start while it is `true`, returning "Detected nested lazycloud execution. Exit this context to start lazycloud"); exiting the shell resumes the app loop, like `s` IAP SSH.

### DNS zones and records

Cloud DNS zones are fetched via `ListProjectDNSZones` (ManagedZones list) and cached in `dns_zones`; records via `ListZoneDNSRecords(projectID, zone)` (ResourceRecordSets list), cached per `(project, zone)` in `dns_records`. The DNS zones view is reached via `:dns` (no numeric shortcut; all ten are taken). Pressing `d` on a zone row sets `appState.Zone`/`appState.ZoneProject` and switches to the zone-scoped records view, the same flow as clusters → workloads; `refresh` re-fetches only the focused zone. `g` opens the Cloud DNS console at the focused resource — the zone details page in the zones views (`GCPDNSZoneURL`, `/net-services/dns/zones/<zone-name>/details`, using the zone Name, not the DNS name) and the record's rrset view page in the records view (`GCPDNSRecordURL`, `/net-services/dns/zones/<zone>/rrsets/<record-name>/<type>/view`, using the record's DNS name as cached — trailing dot included — and its Type column).

### Cloud routers

Cloud Routers are fetched via `ListProjectCloudRouters` (Routers aggregated list; `BgpPeers` → `CloudRouterPeer` with interface/IP/ASN, `Nats` → names, `Bgp.Asn` → `BGPASN`) and cached in `cloud_routers` keyed by `(project, region, name)`, with `Peers`/`NATs` stored as JSON like VM interfaces. The view is reached via `:routers` (`cloud-routers` alias works too; no numeric shortcut). The table shows the router ASN with `Peers`/`NATs` counts; `y`/`v` expose the full peer list via the cached `CloudRouter` JSON, and `g` opens the Cloud Router details page (`GCPCloudRouterURL`, region-scoped like the cluster deep link).

### VPNs

VPN rows are gateways of both kinds: `ListProjectVPNGateways` fetches HA VPN gateways, classic target VPN gateways and all VPN tunnels, grouping the tunnels by gateway self-link (`VpnGateway` for HA, `TargetVpnGateway` for classic) into `Tunnels` (`VPNTunnel` with interface/peer IP/IKE/status/router; the Router short name matches rows in the cloud routers view). Everything is cached in `vpn_gateways` keyed by `(project, region, name)`, `IPs` (HA interface addresses) and `Tunnels` stored as JSON. The view is reached via `:vpns` (`vpn` alias works too; no numeric shortcut). The Type column is `ha`/`classic` like the networks view's Type column; classic rows have no IPs (classic gateway IPs live on their forwarding rules). `y`/`v` expose the full tunnel list via the cached `VPNGateway` JSON, and `g` opens the VPN gateway details page (`GCPVPNGatewayURL`, region-scoped).

### Private Service Connect

PSC rows come from both sides: `ListProjectServiceAttachments` fetches service attachments (published services) via the ServiceAttachments aggregated list and caches them in `service_attachments` keyed by `(project, region, name)`, with `Connections` (`PSCConnection`: consumer endpoint rule, consumer project parsed from the endpoint URL, consumer network, status) stored as JSON like VPN tunnels. Endpoint rows are not fetched separately: they are the cached forwarding rules whose target kind is `serviceAttachments` — `targetRef` recognizes that URL segment, so the PSC refresh (`fetchProjectPSC`) fetches service attachments plus forwarding rules and saves both tables (forwarding rules shared with the LBs view). The view is reached via `:psc` (`private-service-connect` alias works too; no numeric shortcut). Attachment rows show the target producer service and the connected-endpoint count; endpoint rows show the target service attachment (short name), the target PSC's owning project ID (`Target Project` column, parsed via `ResourceProjectName`), the endpoint IP, and the attachment's full reference (`projects/.../serviceAttachments/...`, `ResourcePath`-trimmed) in the Description column — all from `ForwardingRule.TargetURL` (new column on `forwarding_rules`). `y`/`v` expose the cached `ServiceAttachment` (full connection list) or `ForwardingRule` JSON, and `g` opens the console PSC details page — `/net-services/psc/producers/details/<region>/<name>/overview` for attachments, `/net-services/psc/details/<region>/<name>/overview` for endpoints (`GCPPSCAttachmentURL`/`GCPPSCEndpointURL`).

### Instance groups

Rows are instance groups of both kinds: `ListProjectInstanceGroups` fetches managed groups (`instanceGroupManagers` aggregated list → Type `managed`, size = target size, template short name) and unmanaged groups (`instanceGroups` aggregated list → Type `unmanaged`, size = member count, network/subnetwork); a managed group also exposes a same-named underlying instance group, so the unmanaged pass skips `(zone, name)` keys claimed by a manager and the managed row inherits its network/subnetwork. Groups can be zonal or regional — the Location column holds the zone or region short name. Everything is cached in `instance_groups` keyed by `(project, zone, name)`. The view is reached via `:igs` (`instance-groups` alias works too; no numeric shortcut). `y`/`v` expose the cached `InstanceGroup` JSON, and `g` opens the instance groups details page (`GCPInstanceGroupURL`). Pressing `m` on a group row switches to the VMs view filtered to the group's members: `ListInstanceGroupVMs(projectID, location, name)` calls `instanceGroups.listInstances` (zonal vs regional client inferred from the location's dash count, like `ListClusterWorkloads`), members are matched against the cached VMs by `(zone, name)` via `vmsInInstanceGroup`, VMs are fetched first if not cached, and Esc clears the filter — the same flow as node pools' `m`.

### Reservations

Rows are Compute Engine reservations: `ListProjectReservations` walks the Reservations aggregated list (zonal only, rows without a zone are skipped) and maps each to `Reservation` — zone/machine type/commitment as short names, `SpecificReservation.Count`/`InUseCount` → Reserved/In Use columns, `ShareSettings.ShareType` → Share (empty for unshared), `SpecificReservationRequired` → Required, plus status/description. Reservations created from a template (`SourceInstanceTemplate`) have no `InstanceProperties`, so their Machine Type is empty; aggregate (shape-flexible) reservations leave Reserved/In Use at 0. Everything is cached in `reservations` keyed by `(project, zone, name)`. The view is reached via `:reservations` (`res` alias works too; no numeric shortcut). `y`/`v` expose the cached `Reservation` JSON (including Required and Commitment, which the table doesn't show), and `g` opens the reservation details page (`GCPReservationsURL`, `/compute/reservations/detail/<zone>/<name>`, zone-scoped like the instance group deep link).

### Images

Rows are the project's custom Compute Engine images: `ListProjectImages` walks the images list (global resources, no aggregated list) and maps each to `Image` — family, status (`READY`/`FAILED`/`DELETING`/…), `DiskSizeGb` → Size GB, `StorageLocations` joined → Location, `imageSource` picking the first set of `SourceDisk`/`SourceImage`/`SourceSnapshot` as a short name → Source, `CreationTimestamp` → Created (formatted like Updated), description, and `Deprecated.State` → `Deprecated` (kept in the cached JSON and detail filters, not shown in the table). Everything is cached in `images` keyed by `(project, name)`. The view is reached via `:images` (`image` alias works too; no numeric shortcut). `y`/`v` expose the cached `Image` JSON (including Deprecated), and `g` opens the image details page (`GCPImageURL`, `/compute/imagesDetail/projects/<project>/global/images/<name>`).

### Public images

Google's public OS images (debian, ubuntu, rhel, sles, windows…) are owned by dedicated public image projects, so they never appear in a project's own images.list. `viewPublicImages` (view_publicimages.go) lists them: the same `Image` rows/columns as the images views plus the owning project as the Project column, rendered by `imageRowsAll`. The project set lives in `providers.PublicImageProjects` (almalinux, centos, cos, debian, opensuse, oracle-linux, rhel, rocky-linux, suse, suse-sap, ubuntu-os, windows, windows-sql `*-cloud` — probed empirically; `ubuntu-pro-cloud`/`sles-cloud` don't exist, `coreos-cloud`/`gce-uefi-images` list zero images). Public rows share the `images` cache table keyed by the owning public project: `refresh` loops `PublicImageProjects`, calls `ListProjectImages` + `SaveImages` per project (per-project failures are logged and counted, not fatal — the list can drift over time), and the cache readers split on project membership — `ListPublicImages` (`IN`) vs `ListAllImages`, which excludes the public projects so the images-all view stays custom-only. The view is reached via `:public-images` (`pub-images` alias works too; no numeric shortcut); it needs no project selected (the `a` all-projects toggle is a no-op there) and its auto-fetch key is the bare `kind/`, like the projects view. `y`/`v` reuse the cached `Image` JSON, and `g`/`o` open `GCPImageURL` with the owning public project.

### Instance templates

Instance templates can be global or regional, so `ListProjectInstanceTemplates` walks the InstanceTemplates aggregated list and takes the Location from each template's own region field (`Region` short name, `global` when unset — unlike reservations, no rows are skipped). Each maps to `InstanceTemplate`: machine type as short name, `Properties.Disks` → `Disks` (`InstanceTemplateDisk`: device name, short-named source image, size, short-named disk type, auto-delete, boot flag), `Properties.NetworkInterfaces` → `Interfaces` (`InstanceTemplateInterface`: short-named network/subnetwork, internal IP, first access-config NAT IP as external IP) and labels, plus description and creation timestamp. Everything is cached in `instance_templates` keyed by `(project, location, name)`, with disks/interfaces/labels stored as JSON like VM interfaces. The view is reached via `:templates` (`instance-templates` alias works too; no numeric shortcut) — the help panel entry is the short alias because a `:instance-templates` key widens the panel's key column enough to clip the other descriptions at the fixed 60-column panel width. The Boot Image, Disk GB and Disk Type columns come from the boot disk (the disk flagged `Boot`, falling back to the first) and Network/Subnetwork from the first interface. `y`/`v` expose the cached `InstanceTemplate` JSON, and `g` opens the instance template details page (`GCPInstanceTemplateURL`, `/compute/instanceTemplates/details/<name>` for global templates, `/details/regions/<region>/<name>` for regional ones — the Location column value decides, so regional templates disambiguate from same-named global ones). Pressing `m` on a template row switches to the VMs view filtered to the VMs created from it (`showTemplateVMs`): VMs carry their template's short name in `InstanceTemplate` (from instance metadata), so `vmsFromTemplate` matches cached VMs by name, VMs are fetched first if not cached, and Esc clears the filter — the same flow as node pools' and instance groups' `m`, taking the project from the focused row's Project column in the All view like instance groups.

### Disks

Rows are Compute Engine persistent disks. The fetcher (`ListProjectDisks`, Disks aggregated list), cache table (`disks`, keyed by `(project, zone, name)`) and readers (`ListDisks`/`ListAllDisks`/`GetDisk`) predate the view — the VMs views' refresh still fetches both VMs and disks in one pass, and the disks view adds its own fetch core so `u`/`U` refresh it independently (auto-fetch on empty works the same as other per-project views). Regional disks have no zone and are skipped by the fetcher, so the view is zonal-only. `Users` holds the attached VMs as instance short names (comma-joined in the In Use By column); zone/type/source image are short names like the other compute views. The view is reached via `:disks` (`disk` alias works too; no numeric shortcut). `y`/`v` expose the cached `Disk` JSON, and `g` opens the disk details page (`GCPDiskURL`, `/compute/disksDetail/zones/<zone>/disks/<name>;duration=PT1H` — the zonal `<resource>Detail` console route family as `GCPVMURL`; the `;duration=PT1H` matrix param is what the live console appends, it only sets the details page's monitoring chart window).

### Snapshots

Rows are Compute Engine disk snapshots: `ListProjectSnapshots` walks the Snapshots list (global resource per project, like images) and maps each to `Snapshot` — source disk as short name, `DiskSizeGb` → Size GB (the captured disk's size), `StorageBytes` (actual bytes stored, kept in the cached JSON only, not a table column), `CreationTimestamp` → Created (formatted like Updated), `StorageLocations` joined → StorageLocation (JSON only), `Labels` cached as JSON like VM labels so detail filters work (`Labels env=prod`), plus status/description. Everything is cached in `snapshots` keyed by `(project, name)`. The view is reached via `:snapshots` (`snapshot` alias works too; no numeric shortcut). `y`/`v` expose the cached `Snapshot` JSON, and `g` opens the snapshot details page (`GCPSnapshotURL`, `/compute/snapshotsDetail/projects/<project>/global/snapshots/<name>` — the `imagesDetail` deep-link shape).

### IAM policy

Rows are the project's IAM policy bindings, flattened to one row per (member, role) pair: `ListProjectIAMPolicy` calls the Resource Manager v3 `GetIamPolicy` on the project (requested policy version 3, for conditions) and expands each returned `Binding` — `Member` is the principal string as returned (`user:…`, `serviceAccount:…`, `group:…`, `domain:…`, `allUsers`…), `Role` the granted role, `Condition` the binding condition Title falling back to the CEL Expression when untitled (conditional bindings legitimately duplicate a member+role pair with different conditions). The `Type` column is derived at render time from the member's `:` prefix (`iamMemberType`; colon-less members like `allUsers` type as themselves). Everything is cached in `iam_bindings` keyed by `(project, member, role, condition)`, with `SaveIAMBindings`/`ListIAMBindings` (ORDER BY member, role)/`ListAllIAMBindings`/`GetIAMBinding` (first row — a member+role pair with multiple conditions resolves to one binding, like `GetIPAddresses`). The view is reached via `:iam` (`policies` alias works too; no numeric shortcut). `y`/`v` expose the cached `IAMBinding` JSON, and `g` opens the IAM & Admin Permissions page (`GCPIAMURL`, `/iam-admin/iam` — there is no per-binding console deep link, so every row opens the project's page, like reservations).

Buckets carry their own IAM policy: pressing `i` on a row in the buckets views (`showBucketIAM` in view_buckets.go, project taken from the row's Project column in the All view) sets `appState.Bucket`/`appState.BucketProject` and switches to the bucket-scoped `viewBucketIAM` — the same flow as clusters → workloads and DNS zones → records, with `b` returning to the buckets view via the generic `PrevViewKind` shortcut. Rows are the bucket's bindings flattened the same way (one row per member+role pair, condition Title with Expression fallback, Type derived from the member prefix) via `ListBucketIAMPolicy(projectID, bucket)` (storage v1 `Buckets.GetIamPolicy`, requested policy version 3; `BucketIAMBinding` carries the bucket reference), rendered by `bucketIAMRows` (converts to `IAMBinding` and reuses `iamBindingRows`/`iamMemberType`). Everything is cached in `bucket_iam_bindings` keyed by `(project, bucket, member, role, condition)`; `refresh` re-fetches only the focused bucket and the auto-fetch scope is `kind/bucketProject/bucket`. The view has no `:command` or numeric shortcut, like workloads and DNS records. `y`/`v` expose the cached `BucketIAMBinding` JSON, and `g` opens the bucket's console page on the permissions tab (`GCPBucketIAMURL`, `/storage/browser/<name>;tab=permissions`, the same tab matrix param as `GCPBucketURL`'s `;tab=objects`).

### Custom roles

Rows are the project's custom IAM roles: `ListProjectCustomRoles` calls the IAM Admin v1 `projects.roles.list` with `view=FULL` (the only view returning `IncludedPermissions`) and maps each `Role` to `CustomRole` — `Name` as the short name after `projects/<project>/roles/` (`resourceShortName`), plus Title, Stage (`ALPHA`/`BETA`/`GA`/`DEPRECATED`/`DISABLED`), Permissions and the soft-`Deleted` flag. Everything is cached in `custom_roles` keyed by `(project, name)`, with `Permissions` stored as a JSON array like VM interfaces and `Deleted` as an INTEGER flag like `ServiceAccount.Disabled`. The view is reached via `:roles` (`role` alias works too; no numeric shortcut). The Permissions column shows the permission count (the full list is in the cached JSON); `y` exposes the cached `CustomRole` JSON, `v` opens the details window with the permissions printed one per line (`customRoleDetails`, via the `viewDef.details` hook in `showRowDetails`), and `g` opens the role details page (`GCPCustomRoleURL`, `/iam-admin/roles/details/projects%3C<project>%3Croles%3C<name>;returnToCustom=true?project=<project>` — the console encodes the role name's `/` separators as `%3C` in the path, with the `returnToCustom=true` matrix param marking the custom-roles page as the return target).

### Routes next-hop chart

Pressing `c` on a routes-view row (`showRouteHopChart` in view_routes.go, both `viewRoutes` and `viewRoutesAll`) shows the `route` overlay: a mermaid `graph TD` chart — route box → hop diamond (kind: value, destination range as edge label) — rendered as terminal art with `mmaid.Render` (mmaid-go). When the next hop parses as an IP literal (`net.ParseIP`), `routeHopTargets` matches it against the route's project in cache: cached VMs by interface InternalIP/ExternalIP (`vmMatchesIP`, box per VM: `VM: name (zone)`) and cached forwarding rules by IPAddress (rounded box per LB: `LB: name (region, scheme)`); an IP hop with no match renders a dotted edge to an `unknown` box, non-IP hops stop at the hop node. Each LB target continues via `lbBackendsMermaid` + `Cache.ResolveLoadBalancer`: one `fwr: name` box per resolved backend service (URL-map path-rule services included), and one hexagon per backend printing its group name (`group: <Backend.Group>`, already a short name from `resourceShortName`); services or groups missing from cache simply end the branch. `renderMermaidArt` pins the render width by pointing `os.Stdout`/`os.Stderr` at a pipe (so mmaid's TIOCGWINSZ ioctl fails and it falls back to `COLUMNS=80`) and restores both files plus the env afterwards — otherwise the layout stretches to ~2× the real terminal width and overflows the overlay. The overlay uses `a.newArtOverlay` (app.go): like `newOverlay` but `SetWrap(false)` and sized to the art (`artOverlayWidth`: widest line + 2, capped to screenWidth-2, min 10) instead of the fixed 80.

### Load balancer composition

GCP LBs have no single resource: a row = one forwarding rule (`ForwardingRule`, with `TargetKind`/`Target` parsed from the rule's target URL via `targetRef`). `Cache.ResolveLoadBalancer(projectID, region, name)` composes the tree from cache: rule → target proxy (`TargetProxy`) → URL map (`URLMap` with `PathRules`) → backend services (`BackendService` with `Backends` + `HealthChecks`); internal/classic rules target a backend service directly. The fetchers (`ListProjectForwardingRules`, `ListProjectTargetProxies`, `ListProjectURLMaps`, `ListProjectBackendServices`) each save to their own table (`forwarding_rules`, `target_proxies`, `url_maps`, `backend_services`); refresh (`refreshProjectLBs` in view_loadbalancers.go) fetches all four. `selectRow` shows the `lb` details overlay with the full chain; the Backends column shows the default backend service plus `(+N)` extra path-rule services. `lbConsoleURL` picks the console deep link: `loadBalancers` list filtered by URL map name when the chain has a URL map, otherwise the `frontends` list filtered by the forwarding rule name.

Per-project views (`viewX`) use `appState.ProjectID`; the `viewXAll` variants cover all cached projects.

## UI architecture

- Single `tview.Table` (`a.info`) shared by all views. `populateInfoPanel()` (app.go) writes a bold fixed header row (`SetFixed(1, 0)`) + data rows; `applyFilter()` repaints with the active filter.
- Main layout (main.go): summary area (4 rows: project summary + numeric shortcuts panel, three key/desc pairs per row) / `tview.InputField` (`a.cmd`) / info table / infobar / status bar, wrapped in `tview.Pages` (`a.pages`).
- **Infobar** (pkg/app/infobar.go): one-row `tview.Table` (`a.infobar`) between the info table and the status bar showing the current view's available shortcuts, refreshed on every view switch (`setView` → `refreshInfobar`) and config reload. It renders from the same `shortcuts` table as the help overlay: view-scoped shortcuts (the ones whose `visible` predicate holds, e.g. `w` workloads in the clusters views, `c` chart in the routes views, `s` ssh in the VM views) come first, then global shortcuts ordered by `infobarGlobalOrder` (`u`, `U`, `y`, `v`, `g`, `?`, `q`, `:`, `/`, `a`, `space`, `b`, `F1`), deduped by label and fitted to a 160-char budget (`infobarBudget`; overflow pairs are skipped). Numeric keys are never shown (the summary panel already lists them). Descriptions are shortened via `infobarShortDesc` (desc → short label, e.g. `update cache` → `update`, `show row details` → `details`) since the full help descriptions don't fit the single row. Colors reuse the `shortcutLabels`/`shortcutText` theme selectors. The bar is toggleable via the `infobar:` section of `~/.config/lazycloud/config.yaml`: `show_shortcuts: true` (default, seeded on first run like the other sections, preserved when the section exists), loaded in `Run` and applied on `F1` editor exit (`reloadConfig` → `setInfobarEnabled`, which resizes the row between 1 and 0 via `a.mainView.ResizeItem` so the table reclaims the space).
- **Theme**: the `theme:` section of `~/.config/lazycloud/config.yaml` (created with the standard values on first run — migrating a legacy `theme.json` + `shortcuts.json` pair into it when those files exist, both left in place but no longer read — and migrated in place when keys are missing — absent `shortcutLabels`/`shortcutText`/`summaryLabels`/`summaryText`/`statusText`/`detailText`/`activeRowBackground` inherit the file's `labels`/`text` while `statusLabels`, `detailLabels` and `activeRowText` keep their standard values, loaded in `Run` via `providers.LoadConfig` + `applyTheme` in pkg/app/theme.go, before any tview primitive is created because tview captures the style colors at widget creation) sets fourteen color selectors, with invalid color names falling back to the standard values: `labels` (the yellow accents — info table headers → `tview.Styles.SecondaryTextColor`), `text` (the regular text of those sections → `tview.Styles.PrimaryTextColor`), `borders` (info table and overlay borders → `tview.Styles.BorderColor`), `title` (info table and overlay border titles → `tview.Styles.TitleColor`), `shortcutLabels`/`shortcutText` (key and description cells of the shortcuts panel, help overlay and numeric summary panel, set explicitly via `theme.shortcutLabelColor()`/`theme.shortcutTextColor()` in `populateShortcutsPanel`/`newShortcutsSummaryPanel`), `statusLabels`/`statusText` (the status bar: `statusLabels` colors the informational messages written via `a.statusInfo` — per-view `def.status` row-count strings, fetching/refresh notices and the filter-mode hint — applied as `theme.statusLabelTag()`; `statusText` is the status TextView's base color for untagged segments like error details, set via `SetTextColor` in `Run`. Error and success messages stay hardcoded `[red]`/`[green]`.), `summaryLabels`/`summaryText` (the project summary TextView: prefixes and values via `theme.summaryLabelTag()`/`theme.summaryTextTag()` in `renderSummary`/`newSummaryPanel`, base color for untagged segments like the error details of `reportError` via `SetTextColor`; summary error prefixes stay hardcoded `[red]`), `detailLabels`/`detailText` (the details floating windows: `detailLabels` colors the field names in the `*Details` builders (`vmDetails`, `ipDetails`, `lbDetails`, `clusterDetails`, `dnsRecordDetails`) and `appendRowDetails` via `theme.detailLabelTag()`; `detailText` is the overlay TextView's base color for the values, set via `SetTextColor` in `newOverlay` — the help overlay and the route art overlay don't use `newOverlay` and are unaffected), and `activeRowText`/`activeRowBackground` (the info table's selected row, set as `SetSelectedStyle` in `newInfoPanel` via `theme.activeRowTextColor()`/`theme.activeRowBackgroundColor()` — without them tview's default swaps the cell colors, so the background tracks `text` and the text stays black; the standard values `black`/`white` render identically to that swap under the standard theme).
- **Key handling** is two-layered:
  - Global: `a.inputCapture` (handlers.go) — `Ctrl-C` quits, `Esc` → `escapePressed()`, single-letter shortcuts (`shortcuts` table in handlers.go: `u` refresh, `U` refresh all views of the current project — `refreshProjectViews` walks the `projectViewKinds` list (views.go) and calls each view's sync `fetch` core for the current project in one background goroutine, updating the status bar to `Fetching <view title> (i/N)...` per view and reporting `Updated N views for <project>` with a failed-view count at the end —, `y` copy row, `o` open console, `?` help, etc.). The `shortcuts` table is the single source of truth: the help overlay and the numeric summary panel (three key/desc pairs per row) both render from it. The help overlay renders `visibleShortcuts()` sorted by key label — case-insensitive, `sort.SliceStable` on the lowercased `label()` (so `/`, `:`, `?` lead, F1 sorts as "f1", `space` as "space", and duplicate keys keep their declaration order) — and each entry's `commands` sub-rows sorted by command name (`sortedCommands`, a copy so the global slice is untouched; the input capture itself still walks the unsorted `shortcuts` slice). Numeric keys `1`–`9`, `0` switch views per the `shortcuts:` section of `~/.config/lazycloud/config.yaml` (created with defaults on first run; keys map to view names — any `viewKind` string such as `projects`, `vms`, `dns-zones`, `workloads`, `vms-all`, …; loaded in `main` via `providers.LoadConfig` + `applyShortcutConfig` in shortcut_config.go, which rebuilds the numeric entries with desc `"show " + view title` and the action from `viewShortcutAction`; keys absent from the section keep their defaults). The space bar is a fixed global shortcut for the projects view (rendered as `space` in the help overlay via `shortcutKeyLabel`); after rendering the view it activates the bottom filter input (`startFilter`), so typing straight away filters projects — pressing space while the input is focused just types a space, it does not re-trigger. Non-rune keys live in the same `shortcuts` table via the optional `specialKey` field (`tcell.Key`, dispatched on `event.Key()` by the shortcut's `matches` method; the help overlay label comes from `tcell.KeyNames` via `label`): `F1` opens `config.yaml` in the editor (`openConfigFile`, path from `providers.ConfigFilePath` — the same `$EDITOR` with `vi` fallback, `tapp.Suspend` pattern as the log file, shared through `openFileInEditor` in handlers.go) and reloads it on editor exit (`reloadConfig`: `providers.LoadConfig` + `applyShortcutConfig`/`applyTheme`/`applyAutoUpdateConfig` re-run, `staleAutoRefresh` re-set, then `applyThemeToWidgets` re-applies the colours the widgets captured at creation — selected row style, info/cmd/help border and title colours, cmd field style, summary/status base colours — and repaints: `renderSummary`, `refreshShortcuts`, `populateShortcutsSummaryPanel` and `applyFilter`; a broken YAML file keeps the running values and reports `[red]Failed to reload config: …`, and LoadConfig's in-place section merge may rewrite the file as at startup). View-scoped: `w` (workloads of the focused cluster), `d` (DNS records of the focused zone, DNS zones views only), `b` (back to the parent view, workloads/DNS records views only — clusters or DNS zones, honoring `AllProjects`), `c` (fetch cluster credentials via `gcloud container clusters get-credentials`, clusters views only; in the routes views `c` instead shows the next-hop chart — see Routes next-hop chart; in the workloads view `c` instead sets the kubectl context and opens an interactive shell — see Workload fetching), `l` (logs, VM + clusters + node pools + workloads views, dispatches via `openLogs`; in the node pools view it opens Logs Explorer with a `log_id("events")` + `resource.type="k8s_node"` query plus the pool name as a free-text match, via `GCPNodePoolEventsURL`), `e` (clusters views only: opens Logs Explorer with the cluster autoscaler visibility query — `log_id("container.googleapis.com/cluster-autoscaler-visibility")` + `resource.type="k8s_cluster"` plus cluster name and project labels from the focused row — via `GCPClusterAutoscalerLogsURL`/`openClusterAutoscalerLogs`; in the workloads view `e` instead opens the cluster events query — see Workload fetching), `f` (clusters views only: opens Logs Explorer with the admin activity audit query for create methods — `resource.labels.cluster_name`/`resource.labels.project_id` from the focused row, `resource.type="k8s_cluster"`, `log_id("cloudaudit.googleapis.com/activity")`, `protoPayload.methodName=~"create"` — via `GCPClusterCreateAuditLogsURL`/`openClusterCreateAuditLogs`), `s` (IAP SSH, VM views), `r`/`x` (restore/delete project, projects view).
  - Enter on a table row fires `a.info.SetSelectedFunc` → `app.selected()` → the current view's `selectRow`.
- **Global search** (search.go): `S` (not in VM views, where `s` is IAP SSH) or `:search` opens a left search side panel (`buildSearchPanel`: query InputField on top, results Table below) living in `searchColumn` next to the main view — zero-width until open, then `searchPanelWidthFor` gives it 46 columns (2/5 of the width below 100). `/` stays the per-view filter. Esc closes it (`escapePressed` checks `searchOpen` first) keeping the query in `a.searchQuery` for the next open; `Tab` (`toggleSearchFocus`) moves focus between panel and main view with the panel border highlighted while focused (`updateSearchPanelStyle`, `searchFocusBorderColor`). Results come from `a.searchIndex` — a lazily built, app-lifetime index over the All views' caches (`searchKinds`, most-used first: VMs, IPs, VPCs, buckets, ...): each entry is one row plus its project (last column) and the pre-lowered row text. `ensureSearchIndex` queues a background build of every cold or invalidated kind (`markViewUpdated` invalidates the kind via `searchIndexedKind` — per-project kinds map to their All twin — and re-ensures while search is open, so refreshes update live); the builder (`buildSearchIndex`) loads one kind at a time and re-runs the live search after each, so results appear progressively. A kind with zero cached entries is treated as missing data, not empty: `pullSearchKind` fetches it per cached project in the background through the view's normal `fetch` core (one pass per kind per app run — `pulled` map, so a project without VMs is not refetched forever); the saves land through `markViewUpdated`, which invalidates and rebuilds, so hits keep arriving while search is open. An empty project cache is bootstrapped the same way by `ensureSearchProjects` (`providers.ListGcloudProjects` once per app run). Matching (`parseSearchTerms`/`match`) is the filter grammar minus detail paths: space-separated substring terms, all includes must match, `-x` excludes, case-insensitive across the whole row. Hits are capped just above the 100-row display limit (`maxSearchHits`). `refreshSearchResults` renders one bold header row per matching kind (`Kind (N)` with the total count) followed by one indented project subrow per project in that kind's sublist (`searchGroupIndent` spaces, `project (count)` label) — `searchKindSummary` returns the per-project counts, and the row→group (`searchRowGroups`) / row→project (`searchRowProjects`) maps drive selection. Moving the selector previews in the main view (`searchPreview`, wired through `SetSelectionChangedFunc`, only while the panel holds focus): a kind header opens its All view with the query as the live filter, a project subrow additionally appends `+ project` to the filter. Enter (`searchSelect`) lands the previewed view and filter, keeping the panel open as the sidebar: `S` returns to it, Esc closes. `searchResultsRowForProject` maps a kind+project pair back to its subrow. While the search panel has focus, `inputCapture` passes runes through untouched (query text / results navigation).
- **Command vs filter mode**: the bottom InputField is either a filter (`/` prefix or after pressing the filter shortcut, Enter → `filterEnter()`) or a command (`:`, Enter → `commandEnter()`). `commandEnter()` special-cases typed IP literals (`net.ParseIP`) by jumping to the IPs view; single words matching the `viewCommands` map in handlers.go switch views; anything with arguments or an unknown name goes to `runCommand` (commands.go), which clears the input first, dispatches through the `commands` table and reports `[red]Unknown command: <name>[-]` for misses. In cmd mode with the input focused, Tab/Backtab complete the command name (`completeCommand` in handlers.go, same two-phase rotation as filter detail completion): candidates are `commandNames()` — the sorted deduped union of `viewCommands` and `commands` keys — a typed prefix (case-insensitive) completes to the first/last match, and once the text equals a candidate Tab/Backtab rotate through the full candidate list (wrapping); multi-token input (arguments typed) and no-match input are left untouched. First command: `sort asc|desc <col_name>` — the column is matched case-insensitively against the view headers with spaces allowed (`:sort desc machine type`), then `sortRows` sorts `a.visibleRows` in place (stable, case-insensitive cell compare — `allRows` keeps its original order, so any base reset such as Esc, a fresh `/` or a view change returns to cache order) and narrows the filter base to them via `setFilterBase(a.visibleRows)` (same pattern as `/` in refinement mode; resets the detail-resource cache) before repainting via `applyFilter`. The active filter survives the command: `focusCmd` does **not** reset the narrowed `filterBase` (a refinement's `/` press bakes the previous text into the base, so the `exitFilterMode` allRows reset would lose the refined rows — the base and visible rows stay untouched at cmd entry), stashes the input text into `a.savedFilter` plus the `filterStashed` flag, clears the status hint and clears the input. `runSortCommand` restores the session afterwards (`restoreFilter`: whenever a stash is pending — even with empty text, since the refinement may live only in the narrowed base — back to `modeFilter` with the ` / ` label and the filter text re-entered, so `changed` → `applyFilter` re-applies it over the sorted visible rows). An aborted cmd excursion stays recoverable: `/` (`startFilter`) resumes a pending stash before its branch logic, so refinement continues from the still-visible rows instead of starting fresh from `allRows`. The stash is invalidated by `setView` (view switches and refreshes go through it), the Esc filter-clear, and consumed on use. Entering either mode always starts from an empty input: `focusCmd` clears the text after the stash and the mode switch, and `startFilter` clears in both branches. Errors (usage / bad direction / unknown column) land in the status bar as `[red]`, success as `[green]Sorted by <col> <dir>`. Second command: `write <file.(csv|json|yaml)>` — exports the current elements of the info view (`a.visibleRows`, filtered or not) to a file in the working directory: `.csv` via `csvBytes` (encoding/csv, view headers + visible cells), `.json` (indented) / `.yaml` / `.yml` via `resourceBytes` + `viewResources` (each visible row resolved through the view's `resource` and wrapped like the `y` copy — resource fields plus the `Columns` object mapping headers to rendered cells, via `rowCopyPayload`; yaml keys use Go field names, since the wrapper is a map rather than a struct); fails fast on the first resolution error, and json/yaml in a view without `resource` errors with `this view has no resource details`); success reports `[green]Wrote N elements to <file>[-]`, other errors `[red]write: ...[-]`. Filter text is a case-insensitive substring match across all cells; a `-` followed by a space starts an exclusion term (`splitFilterQuery` in app.go, term parsing/matching in filter.go): text before the first `- ` is the include term, each segment after a `- ` is an exclusion that hides rows matching it, e.g. `web - staging - canary`. Empty exclusion segments (mid-typing) are ignored; a dash without a following space is matched literally. A term whose first token (before the first space) is a field path of the view's resource is a **detail filter**: `Labels env=prod` matches only the Labels detail, `ServiceAccounts.*.Email x` matches any element of the ServiceAccounts list by Email, `DataDisks.*.SizeGB 100` by SizeGB. Paths are `.`-separated (`Field`, `Field.*.Sub` where `*` descends into a list/map matching any element, `Labels.key` for map keys); field names match case-insensitively with a singular/plural alias (`ServiceAccount` ≡ `ServiceAccounts`). A term is a detail filter only when its path validates against the view's `samples` and has a space (`env prod` in the VMs view stays a plain substring); resolved resources are cached per `filterBase` in `a.rowResources` (reset by `a.setFilterBase`, built lazily by `resolveRowResources` only when a detail term is present) and matching never touches row cells for detail terms. Values render as strings (`k=v` joined by `,` for maps/sorted structs), so `Labels env=prod` matches the `env=prod` pair. In filter mode, Tab/Backtab cycle the view's available detail paths (`detailPaths` in filter.go reflects over `samples`; struct fields, `*` for list-of-struct element descent, maps/scalar slices terminal, sorted): `completeFilterDetail` (handlers.go) completes a partial head (the text before the first space, case-insensitive prefix of a path) to the first (Tab) or last (Backtab) matching path, prepends the first/last path when the head matches nothing, rotates a head that already equals a path to the next/previous one keeping the rest, and drops the prefix when rotating past the last/first path. The hook lives in `inputCapture` before the cmd-focus early return, so Tab works both while typing and in refinement mode (focus on the table); `SetText` fires `changed` → `applyFilter`, so each rotation re-filters live.

## Overlays (floating windows)

Built on `tview.Pages` (stacked, hidden/shown pages), centered with spacer-Flexes:

- `help` page — `newHelpOverlay()` (handlers.go), toggled by `?` (`toggleHelp()`). tview's `Pages.ShowPage`/`HidePage` re-delegate focus to the topmost visible page, so the help table takes focus while open (PgUp/PgDn scroll it) — and on close `toggleHelp()` must `SetFocus(a.info)` itself, because the main layout is a Flex whose items were all added with `focus=false` and `Flex.Focus` would otherwise fall back to the bare Box, leaving the info table unfocused.
- `vm` page — VM details window, opened via VM views' `selectRow` → `showVMDetails()` (view_vms.go). `vmDetails()` builds the `[yellow]label: [-]value` color-tagged text.
- `ip` page — IP address details window, opened via IP views' `selectRow` → `showIPDetails()` (view_ips.go). `ipDetails()` formats all cached `IPAddress` fields.
- `lb` page — Load balancer details window, opened via LB views' `selectRow` → `showLBDetails()` (view_loadbalancers.go). `lbDetails()` renders the composed rule → proxy → URL map → backend services chain.
- `dns` page — DNS record details window, opened via the DNS records view's `selectRow` → `showDNSRecordDetails()` (view_dnsrecords.go). `dnsRecordDetails()` renders all cached `DNSRecord` fields with one data value per line.
- `cluster` page — Cluster details window, opened via the clusters views' `selectRow` → `showClusterDetails()` (view_clusters.go). `clusterDetails()` renders all cached `Cluster` fields with one node pool per line (name, version, node count).
- `route` page — Routes next-hop chart window, opened via `c` in the routes views → `showRouteHopChart()` (view_routes.go). See Routes next-hop chart.
- All are dismissed by `Esc` — `escapePressed()` (handlers.go) removes the front page if it is `"vm"`, `"ip"`, `"lb"`, `"dns"`, `"cluster"`, `"route"`, or `"row"`, and refocuses the table.

**Pattern to add a new floating window**: use `a.newOverlay(title, content)` (app.go) — it builds the border+title dynamic-colors `TextView`, caps height to the terminal (`overlayHeight`: lines+2, at most screenHeight-2, min 3) and width (`overlayWidth`: 80, at most screenWidth-2, min 10; screen size captured from `SetBeforeDrawFunc` in main.go), and returns `(overlay, text)`. For pre-rendered art that must not wrap, `a.newArtOverlay` is the same pattern with `SetWrap(false)` and width sized to the content (`artOverlayWidth`). Then `a.pages.RemovePage(name)` + `AddPage(name, overlay, true, true)` + `a.tapp.SetFocus(text)` so arrows/PgUp/PgDn scroll long content; add the page name to the Esc dismissal check.

## Data model & cache

Resource structs live in gcloud.go (e.g. `IPAddress` has `ProjectID, Name, Address, AddressType, Status, Region, Subnetwork, Network, UpdatedAt`). Fetchers follow `ListProject<Res>(projectID)` naming (e.g. `ListProjectIPAddresses` returns global + regional addresses; `ListClusterWorkloads` is the shell-out exception). Short names for GCP resource URLs come from `resourceShortName`; load balancer target URLs are split into kind + name by `targetRef`.

The cache (cache.go) mirrors each struct to a SQLite table (e.g. `ip_addresses`) with upsert-on-conflict. `view_updates` (cache.go) is the one non-resource table: one row per `(view kind, project)` — the project the update was done for and the date the view was last refreshed for it (`PRIMARY KEY (view, project_id)`, `updated_at` empty until first refresh, so updating a view in labs and dev-apps keeps two independent entries). `Run` seeds all registered kinds (`SeedViewUpdates`, baseline rows under empty project), every successful refresh upserts via `a.markViewUpdated(kind, projectID)` → `Cache.SaveViewUpdate`, and `Cache.GetViewUpdate(view, projectID)` reads it back — all views, old and new, need an entry in this table. Reads: `ListX` (one project), `ListAllX` (all), `GetX` (exact lookup, may return multiple rows — e.g. `GetIPAddresses` one per subnetwork); workloads are the cluster-scoped exception (`ListClusterWorkloads(projectID, cluster)`). Views always read from cache; `refresh` repopulates from the API in a goroutine and calls `QueueUpdateDraw` to repaint. When `setView` renders a view with zero rows it auto-triggers that view's `refresh` once per scope (`autoFetchIfEmpty` in app.go, keyed by `autoFetchKey`/`autoFetchScope`: `kind/project` for per-project views, `kind/clusterProject/cluster` for workloads/node pools, `kind/zoneProject/zone` for DNS records, bare `kind/` for the projects, public-images and all-projects views) — the mark lives in `app.autoFetched`, initialized only in `Run` (nil in tests, which disables the trigger), so a fetch that completes still-empty or fails cannot loop; `u` marks the current view and `U` marks every per-project kind for the project before fetching, and `x` marks the projects key so deleting the last cached project is not immediately undone by an auto-fetch. When the empty-trigger does not fire, `setView` also auto-refreshes stale data (`autoRefreshStale` in app.go, gated by the Run-only `staleAutoRefresh` flag — false in tests): if the view's `(kind, project)` `view_updates` row is older than 60 minutes (`staleViewAfter`; `viewUpdateStale` treats missing or unparseable dates as stale), the view's `refresh` runs for that project — the project from `viewUpdateProject` (scoped kinds → their cluster/zone/bucket project, else `appState.ProjectID`), and only per-project kinds plus the four scoped kinds are eligible (`viewRefreshesProject`); all-projects variants, projects and public-images skip it since their refresh is multi-project. The stale trigger marks `autoFetched` like the empty one (so a fetch that completes empty cannot double-fire), but the rule is time-based, not session-based: a failed fetch retries on the next view entry, a successful one stamps a fresh date and further triggers stop, and after another hour the view refreshes again. The trigger and its threshold come from the `autoupdate:` section of `config.yaml` — `enabled` (`false` turns the stale trigger off entirely; it is what `Run` feeds the `staleAutoRefresh` flag) and `threshold_in_minutes` (`applyAutoUpdateConfig` in app.go sets the `staleViewAfter` var from it; zero or negative values fall back to the built-in 60): the section is written with the defaults `enabled: true` / `threshold_in_minutes: 60` on first run, added in place to existing config files that lack it (an explicit section is preserved as-is), and defaults apply on the legacy theme.json/shortcuts.json migration path.

`console.go` builds GCP Console URLs per resource (`GCPVMURL`, `GCPAddressesURL`, `GCPVMLogsURL`, `GCPLoadBalancerURL`/`GCPLoadBalancerFrontendURL`, `GCPClusterURL`, `GCPWorkloadOverviewURL`, `GCPWorkloadLogsURL`, `GCPRoutesURL`, `GCPFirewallsURL`, `GCPDNSZoneURL`, ...) — used by the `o`/`g`/`l` shortcuts. Most list-page deep links encode a `pageState` filter (see `GCPAddressesURL`, `gcpLBListURL`).

## Conventions

- No comments in code; keep it that way.
- New view fields are optional function fields on `viewDef` — views without a behavior leave them nil.
- Tests live next to the code (`*_test.go` in both packages); run `mise run test` before considering work done.
- Background work (API fetches) uses `a.tapp.QueueUpdateDraw` to touch UI state; errors during fetch go through `a.reportError` (status + log), never panic.
